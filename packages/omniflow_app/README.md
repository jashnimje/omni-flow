# omniflow_app

Flutter client for OmniFlow, Android only. Design: `../../docs/DESIGN.md`.

The engine runs in a `connectedDevice` foreground service (`flutter_foreground_task`), so flows keep firing with the screen off and after the app is swiped away. The service's task runs in its own Flutter engine and isolate, and it is the only place that opens the database. The UI reaches it only through `EngineClient`: `ServiceEngineClient` sends JSON command and event messages over the plugin's data channel (`lib/service/`). The notification's Stop button stops the service, and the app then shows a Start screen.

While the service runs it holds a Wi-Fi multicast lock (`MulticastLockBridge.kt`, channel `omniflow/multicast`) so broadcast replies and board hellos arrive, plus the plugin's partial wake lock and Wi-Fi lock. The service restarts at boot and after an app update.

A device whose driver pairs in the app (an Android, LG or Samsung TV, a Hue light) has a Pair item in its menu, which shows the engine's prompt and runs `device.pair`. Home Assistant pairs by storing a token, so it has no Pair item, and Setup steps asks for the token in a masked field. A scan lists a Hue bridge or Home Assistant instance that another device already uses, labelled with that device, so the next light or entity behind it can be added. Board pin sheets pick GPIOs from `board.describe`, show its strapping pin warnings when they open, and have an active-low switch for relays.

Rules are built on the Flows tab with New rule: WHEN cards, ONLY IF cards and a THEN list of steps (do, toggle, wait, wait until with its own timeout steps, if and otherwise, do together, set a variable, notify, run). Test run sends the rule to `automation.dry_run` and shows each step by the label the trace gives, or its node id when there is none. Save stays off while an If has no condition or THEN step, or a Do together branch is empty, and marks that card. Save sends the rule to `automation.save`, trusted for a new rule or an approved one. A new rule named like an existing rule asks before replacing it. A stored rule reopens from `automation.get`, and one an agent wrote that waits for approval says so, is saved untrusted and opens its review page, so the builder never approves it. A Notify step shows at the bottom of the screen while the app is open (`flow.announce`). Phone notifications are not built. The builder cannot yet write any-of, not, a compare on the trigger's message, an event match, mode or cooldown. It keeps them when it reopens a rule that has them. The rule JSON is the engine's stored rule form (`lib/rules/rule_spec.dart`), and `test/real_rules_test.dart` checks it against the engine's normalizer. Links keep their link sheet.

The Add button lists what `thing.add` finds and follows its `next` steps: pair with `device.pair`, secrets with `secret.set` in masked fields, settings with `thing.configure`, a board's pins in the pin sheet. Optional keys on the done step get their own fields, a secret masked. Setup steps in a device's menu resumes from `thing.next`. The drivers `thing.add` lists under `manual` (no discovery) open the driver sheet with that driver picked, and Pick a driver by hand opens it empty. The sheet adds with `device.add` and then follows its `next` the same way. A virtual driver such as a place or a person takes no address, and a setting typed as JSON (a place's Wi-Fi `{"ssids": [...]}`) goes as JSON. It stays on `device.add` because `thing.add` refuses a second device behind one hub, which shares the hub's address and stable id.

NFC uses `nfc_manager` in reader mode while the app is in front and sends each tag as `nfc.scanned` with source `phone`, its records as the engine takes them: the type name format's number, and the type and payload in hex. The engine decodes them. A tag written from a tag thing's menu gets the NDEF records `tag.write_payload` returns, byte for byte (an `omniflow://tag/` URI record and an Android Application Record), and the `NDEF_DISCOVERED` filter on that URI opens the app for it when it is closed (`MainActivity.kt`, channel `omniflow/nfc_intent`). That activity is exported, so any app can start it with a made-up NDEF intent. `MainActivity` ignores the intent's id and message extras, reads the tag again through `Ndef.connect`, and passes on only a scan that read succeeded for, marked `live`. The Dart side drops any other scan on the channel. A `tag.unknown` event offers to name the tag through `thing.add`. The service feeds the phone thing its battery and Wi-Fi with `phone.battery` and `phone.wifi` (`PhoneSensorsBridge.kt`, channel `omniflow/phone_sensors`). Android names the Wi-Fi network only with location access, which the phone's menu asks for. Every new engine call is in `lib/api/engine_calls.dart`.

```sh
flutter analyze
flutter test
flutter run            # on a connected Android phone
```

Not yet proven on a phone: the APK build (the Android SDK is not installed), the service surviving a swipe, an hour with the screen off and a reboot, plugins (path_provider, flutter_secure_storage) inside the service isolate, the multicast lock channel, NFC reading, writing and the tag intent, the phone sensors bridge and the location prompt, and battery drain. The Kotlin in `android/` has not been compiled.
